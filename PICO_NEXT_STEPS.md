# Pico-ROS: план продолжения

Дата фиксации: **16 октября 2026 года**. Работа остановлена на паузу.
Этот файл — точка продолжения, а не разрешение на новые аппаратные действия.

## Что уже готово

- [x] Выделена [общая основа прошивок](pico_firmware/README.md): Pico SDK,
  FreeRTOS, USB/Zenoh, запуск Pico-ROS и общие правила сборки.
- [x] Описание платы, пины и драйверы отделены от прикладной логики.
  Поддержан и аппаратно проверен только запасной KAmod RP2040.
- [x] Сохранено одно [проверочное приложение](helpers/rmw_zenoh_pico_spike/firmware_picoros/README.md)
  с двусторонним обменом через штатный ROS CLI. Исполнительных механизмов в нём нет.
- [x] Новая основа прошита на запасной плате. Проверки команд/подтверждений,
  локального таймаута, повторных/старых номеров и некорректного значения прошли.
- [x] Выполнен один перезапуск экспериментального роутера: обмен восстановился
  без перезагрузки MCU, перепрошивки и ручного переподключения USB.
- [x] Удалены устаревшие варианты приложения, одноразовые пробы и временные
  сборочные деревья. Сохранены нужные патчи, регрессионные тесты и история.
- [x] После очистки сборка проходит; канонический UF2 побайтово совпадает
  с прошитым и проверенным образом.

Общая основа — **общие исходники и сборка, не один UF2 для всех плат**.
Рабочие контроллеры `pico_ware_*` не мигрированы и не затронуты.
Новый механизм reconnect и собственный протокол ROS не добавлены.

## С чего начать следующую сессию

1. Прочитать [правила репозитория](AGENTS.md), этот план и
   [актуальные результаты](wiki/picoros_zenoh_production_readiness.md#shared-foundation-hardware-regression-2026-10-16).
2. Без перезапуска проверить состояние контейнера роутера, его image/config,
   наличие нужного USB by-id и соответствие платы сохранённому идентификатору.
3. Если плата подключена, прочитать uptime, текущий ack и состояние команды
   штатными ROS-командами внутри Docker. Последний зафиксированный ack — **602**;
   после перерыва его нельзя считать текущим без чтения.
4. Согласовать следующий эксперимент. Предложение: измерить ресурсы и тайминги
   существующей одноядерной прошивки, не менять сразу архитектуру и reconnect.

## Предлагаемые следующие этапы

### 1. Одноядерная базовая линия

- [ ] Согласовать нагрузку, длительность и критерии измерения.
- [ ] Добавить минимальную диагностику свободной/min-ever кучи и stack
  high-water задач; не создавать новый health/reconnect-протокол.
- [ ] Измерить задержку command → ack, стабильность телеметрии и выполнение
  локального таймаута при согласованной нагрузке.
- [ ] Отдельно учитывать размер ELF/BSS и реально измеренные ресурсы:
  размер статической кучи не равен свободной памяти во время работы.
- [ ] После изменения прошивки выполнить короткую регрессию на запасной плате
  и записать параметры, SHA-256 образа и результаты в wiki.

Результат этапа: воспроизводимая базовая линия с измерениями, а не обещание
production-ready. Сейчас используется одно ядро и куча FreeRTOS 128 KiB;
инструментирование ресурсов ещё не реализовано.

### 2. Только при необходимости — отдельный двухъядерный эксперимент

- [ ] По результатам базовой линии решить, нужен ли SMP вообще.
- [ ] Если нужен, отдельно согласовать эксперимент и проверить совместимость
  USB/Zenoh, разделяемого состояния и задач до аппаратного запуска.
- [ ] Сравнить с одноядерным вариантом и сохранить простой путь отката.

Текущая USB-реализация проверена для одного линка/исполнителя, не для SMP.
Включать второе ядро по умолчанию пока нельзя.

### 3. Подготовка первого прикладного контроллера

- [ ] Выбрать первый контроллер вместе с пользователем и описать его ROS-типы,
  QoS, частоты, требования к времени и поведение при потере/устаревании команд.
- [ ] Добавить только необходимый профиль платы, драйверы и приложение,
  переиспользуя общую платформу без копирования SDK/USB/Zenoh-настройки.
- [ ] Для приводов отдельно определить локальный безопасный останов, E-stop,
  поведение после reboot и защиту от старых команд; проверить откат прошивки.
- [ ] Переносить контроллеры по одному, не заменять все рабочие прошивки разом.

Историческое предложение: knives при физически отключённом питании мотора,
затем IMU и wheels; INA226/RP2350 — отдельный порт. Это **не разрешение**
на подключение моторов или прошивку рабочих плат; порядок нужно подтвердить.

## Что остаётся отложенным, а не пройденным

- Повторная матрица отключений USB/роутера и строгий срок восстановления.
- Исправность встроенных native health-событий после reconnect.
- Корректное graceful shutdown роутера: проверенный stop завершился
  принудительно через 5 секунд, код 137.
- Проверки на целевой Raspberry Pi/ARM64 и production-развёртывание.

Эти проверки ранее исключены из текущего этапа по решению пользователя.
Не возвращать их автоматически в ближайшую сессию; перед production отдельно
согласовать закрытие соответствующих рисков. Старый список «Next execution
order» внизу readiness-документа не отменяет это решение.

**Известный дефект:** после восстановления обмена native-диагностика может
показывать `connected=0, opened=1, closed=1`. Трафик работает, но повторное
открытие не отражено корректно. Не использовать `connected` как единственное
условие исправности или разрешения приводов. Тест-воспроизводитель этого
дефекта не означает, что health gate пройден.

## Сборка и контрольный образ

Из корня репозитория, через существующую Docker-обёртку:

```bash
./helpers/rmw_zenoh_pico_spike/build_picoros.sh
```

Цель: `picoros_usb_connectivity`.

UF2: [picoros_usb_connectivity.uf2](helpers/rmw_zenoh_pico_spike/build/firmware_picoros_connectivity_sdk220/picoros_usb_connectivity.uf2).

SHA-256 проверенного образа:
`d5c50234f849babed39d267c6e03ae4748d78f41f40467b8e7274b7b43cd1edb`.

Плата: flash ID `0xE464C498C3380C35`, USB by-id
`usb-Raspberry_Pi_Pico_E464C498C3380C35-if00`. Номер `ttyACM*` не фиксировать.
Перед прошивкой заново проверить идентичность; BOOTSEL — с участием пользователя.
Без изменения образа повторная прошивка только ради продолжения не нужна.

Не запускать старый `build.sh` без необходимости: он пересоздаёт helper build
и удаляет результаты Pico-ROS. Подробности — в README приложения.

## Что сохранить на время перерыва

- По последней проверке работает `ros2_zenoh_router` с образом
  `relobot-zenoh-serial-accept:experimental`; исходный production-тег не заменён.
- Экспериментальный запуск использует временный override и конфигурацию
  `/tmp/picoros-bidirectional-router.json5`. Обычный Compose recreate/up может
  вернуть stock-образ; не выполнять его вслепую.
- Подключение устройств: `/dev:/hostdev:ro` и cgroup `c 166:* rwm`.
  Проверять разрешение by-id внутри контейнера; стабильное имя не сохраняет
  открытый файловый дескриптор после переподключения.
- Локальные доказательства и rollback лежат в
  `/tmp/picoros-foundation-hardware-20261016-gHQpcv/`; указатель —
  `/tmp/picoros-foundation-hardware-evidence-dir`. Это временное хранилище,
  не долговечный архив. Перед чисткой `/tmp`/перезагрузкой сохранить нужные
  образы и логи в согласованное постоянное место.
- Во время паузы не выполнять новые flash/restart/USB-тесты и не удалять
  временные файлы, от которых зависит текущий экспериментальный запуск.

## Постоянные ограничения и ссылки

Все сборки, тесты и ROS-команды — внутри Docker; хост только оркестрирует.
Для аппаратных проверок использовать штатный `ros2 topic pub/echo`, только
запасной KAmod, без параллельного чтения tty и произвольных reset-байтов.
Не добавлять собственный reconnect-supervisor и не дублировать протокол ROS.
